# Series Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make vector-valued data a first-class part of a formula, so that sieve analysis and grading curves (a series of values over a domain) can be written, evaluated, traced, rendered and documented the way scalar formulas already are. That covers per-element arithmetic, cumulative sums, reductions, per-element rounding and conformity, snapping a computed value to a permitted set, splicing two curves, and binning raw observations.

**Architecture:** A series is a new family of expression nodes (`SeriesNode`) beside `Node`, and not a kind of `Node`. Its length `N` is part of its type, and each element may be absent on its own. Series nodes evaluate to `EvaluatedSeries<Rep, N>` through their own `checked_evaluate_series_si` overloads. Reductions (`sum`, `interpolate_at`) and `snapped` are ordinary `Node`s, and they are the bridge from a series back into the scalar world. That bridge is why a method, an overlay and a vocabulary reach series with no new top-level concept. Each series operation records **one** trace step that carries its whole vector, so a trace grows with the size of the formula and not with the length of the series.

**Tech Stack:** C++23, header-only. Catch2 via CPM. `STATIC_REQUIRE` for compile-time behaviour, plus the `test/negative/` must-not-compile harness, whose asserted message strings are tested API.

**Spec:** `docs/superpowers/specs/2026-09-23-formula-cpp-design.md`: §12 (series designed in from the start), §16.3 Tier A #2 (rounding may differ per element) and #5 (the series operations), §16.1 (limit tables are master data), §16.6, §17 row 12, §11 (the two trace scars) and §19 (the "series/grading curves" guide).

**Read before any task:** `.superpowers/sdd/2026-09-25-methods-and-overlays/defect-classes.md`. Every task below names the classes its steps are built to prevent. Every implementer's report says, for each of the eight classes, what they checked and how.

## Design decisions, and the lead's rulings

The spec settles *what* a series must do (§16.3 #5) and says nothing about *how*. Each decision below gives a recommendation, the reason for it, and the lead's **Ruling** (2026-09-26). Decisions marked **SPIKE** depend on a compiler measurement, which task 1 makes. Task 2 does not start until task 1's findings have confirmed the SPIKE items or the lead has amended them. S14's exact spelling is **decided by** the spike.

### S1. Length is static: `series<Q, N>`, with each element individually absent. **SPIKE**

**Recommendation:** a series' length `N` is a template argument of every series node, and `MeasuredSeries<Q, N>` holds exactly `N` elements. A screen the lab did not use is an **absent element**, not a shorter series. Binning's raw observations are the one exception (S9).

**Why:**
- §16.1 says test methods are code. A method's domain, meaning the set of screens it prescribes, is part of the method and not data.
- With `N` in the type, a length mismatch between two series is a compile error that names both lengths. It never becomes an out-of-range read.
- Evaluation is `noexcept` throughout. A `std::vector` allocating inside it turns `bad_alloc` into `std::terminate`, which is exactly the abort path this project forbids.
- `STATIC_REQUIRE` testing works as it does for every other node kind.

**What the spike must measure (task 1):**
- The constant-evaluation budget. Take a 20-element and a 64-element `Rational` series through three elementwise operations, a cumulative sum and a sum, inside one `STATIC_REQUIRE`, on cl (default `/constexpr:steps`), clang-cl, clang++ and g++ (`-fconstexpr-ops-limit`).
- Whether a transient `std::vector` in a constant expression works on all four compilers. This is only for comparison, if S9 is ruled the other way.

If cl runs out of budget below N = 20, the recommendation still holds, but tests must switch to runtime `REQUIRE` above the measured N. The spike reports that N.

**Ruling: accepted.** Static length, with each element individually absent. When a product specification (master data) uses only some of a method's points, the method still declares the full `N` and the unused elements are *absent*: **the length never comes from runtime data.**

**Spike result (task 1, `task-1-spike.md`): confirmed, with one correction.** The library's real scalar path fits about **1,800 node-evaluations** in one constant expression on clang-cl and clang++ 22.1.3, and about **2,200** on cl 19.51. g++ 13.3 and 14.2 hit no limit at 7,168. Each failing size was bracketed by a passing one, with a failing control. **clang runs out first, not cl** as this section first assumed. The rule is now: keep N × (nodes per element) under about 1,000 per `STATIC_REQUIRE`, and use runtime `REQUIRE` above that (Global Constraints).

### S2. Storage: the series lives in the entry and the node, not in the quantity

**Recommendation:**
- The input is `MeasuredSeries<Q, N>`, which holds `std::array<Measured<Q>, N>`.
- An evaluated series is `SeriesValue<Rep, N>`, which holds `std::array<std::optional<Rep>, N>` in coherent SI.
- `Quantity<...>` does not change.
- The spec's "the value type is a parameter" is met by the *entry* and *node* types (`MeasuredSeries`, `series<Q, N>`), not by a fifth `Quantity` parameter.

**Why:**
- `Measured<Q>`'s invariant is "in `Q`'s declared unit, no unit of its own" (`measured.hpp:19,27`). It then holds per element with no change.
- §8's declaration spelling was settled by measurement and is left alone.
- `Environment`'s `RequireDistinctQuantities` already refuses a scalar and a series of the same `Q` in one environment.
- The rejected alternative is a `SeriesQuantity<Tag, …, N>` CRTP. It puts the length on the *meaning* and makes it impossible to hold one quantity over two domains. Splicing needs exactly that.

**Ruling:** no separate ruling was needed; S2 follows from S1 as accepted.

### S3. A series is not a `Node`. **SPIKE**

**Recommendation:** add `struct SeriesNodeBase {}` and `concept SeriesNode`, disjoint from `NodeBase`/`Node`. Every series node declares `static constexpr Dimension dimension` (the dimension of each element) and `static constexpr std::size_t length`.

**Why:**
- Every `Node` promises `checked_evaluate_si → Evaluated<Rep>`, a scalar (`evaluate.hpp:150`).
- The shipped operators, `checked_evaluate`, `variant<Tag>` and `rounded<>` are all constrained on `Node`. Deriving series from `NodeBase` would let a series stand silently where a number stands.
- Kept apart, a series in a scalar position is a compile error, and task 2 makes it a message in this library's words.

**The spike measures** whether the new operator overloads are unambiguous on all four compilers against the shipped `Node op Node` and `Node op Rational` / `Rational op Node` sets (`expression.hpp:212-303`). The overloads are `SeriesNode op Node`, `Node op SeriesNode`, `SeriesNode op SeriesNode`, `SeriesNode op Rational` and `Rational op SeriesNode`. The spike also tries `constant<unit::Percent>(rat(100)) - series<…>`.

**Ruling:** no separate ruling was needed; confirmed or amended by task 1's overload probe.

**Spike result: confirmed.** Every listed pairing compiles unambiguously on cl 19.51, clang-cl and clang++ 22.1.3, g++ 13.3 and 14.2. A scalar dimension mismatch beside them still draws exactly one message, the shipped one. The operators were compiled in a probe namespace found by ADL, and placing them in `namespace formula` is task 4's to compile.

### S4. "Map" means elementwise lifting. A general `map(series, expression)` is deferred

**Recommendation:** in phase 12, the phase row's "map" means these series nodes, each recording **one** trace step:
- elementwise `+ − × ÷` and negation, with a scalar operand broadcast to every element;
- per-element rounding (task 6).

A general `map(series, <any scalar expression over each<Q>>)` is **not** built this phase.

**Why:** the trace of a general map is either O(N × expression size) or it hides inputs:
- If it records one sub-derivation per element, a twenty-screen analysis gains a hundred steps for a five-node expression.
- If it records only the vectors in and out, the scalar inputs the expression read (a total mass, say) never appear in the derivation, and an auditor cannot reproduce the number.

Elementwise lifting has neither problem: `series<R, 5> / var<Total>` records the series once, `m_t` once and the division once.

**Ruling: accepted.** A general `map` is deferred. Nobody can confirm that no consumer needs a per-element lookup or conditional, so it is recorded as the follow-up **F1: per-element lookup / conditional over a series** (see "Follow-ups" at the end). Nothing in this phase is designed around it.

### S5. Trace: one step per operation carrying the vector, and elements count against `maxSteps`. **SPIKE (for `sizeof(Step)`)**

**Recommendation:**
- A series step carries its value in a new `Step::elements` (`std::vector<std::optional<Rep>>`). A curve step also fills `Step::domainElements`. A failure fills `Step::failedElement`. `Step::value` stays empty for a series step.
- `render_trace` renders the elements inline on the step's line. **Each element shown costs one unit of `maxSteps`**, just as each line does today. A series that does not fit ends with `... k more`, where `k` is the exact count left out, and the existing footer then counts the steps that were cut.

**Why:**
- The §11 scar "always bound rendered steps" was earned by one unusable line. A 256-observation step printed in full on one line is that line again.
- Adding a second required option (`maxElements`) would break every existing `render_trace` call site in the tests, the examples and the docs.
- A defaulted option is "a limit someone forgets", which `trace_render.hpp`'s file comment refuses in so many words.
- Sharing the one required budget keeps the rule the file already states: the caller chooses one number, and nothing unbounded prints.

**The alternative** is a new required `TraceRenderOptions::maxElements` of a `StepLimit`-like type. That is honest, and it costs a sweep of every call site.

**The spike measures** `sizeof(Step<Rational>)` before and after the new fields, on cl and g++. The recorder builds one `Step` per node, so the growth matters.

**Spike result:** `Step<Rational>` grows from 776 to 896 bytes (+120, +15.5 %), identical on cl 19.51 and clang++ 22.1.3 (MSVC STL) and on g++ 13.3 (libstdc++). Every step pays it, scalar ones included. Accepted; the side-record alternative is noted in `task-1-spike.md` and not proposed.

**Ruling: accepted, with one condition.** A truncated element list must say so **in every dialect that can show one**, with a count of what was left out, for example `... 12 more`. Silent truncation would be defect class 1 applied to the trace, and it is tested (task 3, step 1).

What "every dialect" covers here, because the surfaces differ:
- `render_trace` has one dialect today, plain text, and it carries the count.
- The gallery's worked sections put trace output into Markdown pages, and they must carry the same count.
- `render()` and `document()` in Plain, Markdown and LaTeX never truncate a formula's own declared rows. A formula's text is the formula, as it is for lookups today. If any of those three surfaces ever shows element *values*, it must carry the count too, and task 3's test covers each dialect that does.

### S6. Series reach a sink through optional `series_entered` / `series_produced`. **SPIKE**

**Recommendation:** this follows the established shape (`branch_taken`, `constraint_entered`, `variant_entered`). The evaluator asks `if constexpr (requires { sink.series_entered(node); sink.series_produced(node, result); })`, both in one `requires`, so a sink defines both or neither. `NullSink` defines neither and pays nothing. A consumer's sink written before this phase keeps compiling. `entered`/`produced` stay constrained on `Node`, which is still true.

**The spike compiles** this shape on all four compilers with `RecordingSink`, `NullSink`, and a consumer sink that defines only `entered`/`produced`.

**Ruling:** no separate ruling was needed; confirmed or amended by task 1's hook probe.

**Spike result: confirmed** by building and running on cl 19.51, clang-cl and clang++ 22.1.3, g++ 13.3 and 14.2:
- `NullSink` and a consumer sink constrained on `Node` are told nothing and compile.
- A sink defining only one of the two hooks is told nothing.
- A recording sink is told both.

### S7. Absence is decided at the granularity of the output

**Recommendation:**

| Operation | An absent input element makes… |
|---|---|
| elementwise `+ − × ÷`, negation, per-element rounding | that element absent, and no other |
| `cumulative<FromFirst>` / `<FromLast>` | that element and every later running total, in the running direction, absent |
| `sum`, `interpolate_at`, `splice` | the whole result absent |
| `conformity` | that element `NotChecked`; the others are judged |
| an absent **scalar** operand broadcast to a series | every element absent |
| binning | cannot happen: an observation that was not made is not an observation (S9) |

**Why:** this is the library-wide rule, "a formula with one missing input has no answer, and producing one from the inputs that happen to be present is precisely the wrong number" (`measured.hpp`, `combine`), applied at the size of what is produced. A skip-absent `sum` would silently redefine Σ as "Σ of what someone happened to enter".

**On `interpolate_at` specifically:** Strictness makes a whole curve unusable when one screen far from the interpolation point is absent. The recommendation is to stay strict and let the author write the curve without that screen. A lenient rule would have to state which neighbours count, and that is method algebra.

**Ruling: accepted, with `interpolate_at` strict.** Recorded as the follow-up **F2: bracket-only absence for interpolation**, meaning only the two elements around the point would need to be present.

### S8. An arithmetic error in any element fails the whole series, and says where

**Recommendation:** `EvaluatedSeries<Rep, N>` is `std::expected<SeriesValue<Rep, N>, SeriesFailure>`, where `SeriesFailure { ArithmeticError error; std::size_t element; }` gives the zero-based position in the series the failing step produces. The one exception is binning, where it is the position of the observation.

A reduction relays the failure to the scalar channel as its `ArithmeticError`. The position survives in the trace (`Step::failedElement`), because the scalar channel is `Evaluated<Rep>` and widening it for every node kind is the change phase 10 refused to make (`lookup.hpp:80-100`). There is no partial vector: a series with one wrong element is not a series of right ones.

**`checked_evaluate_series` has no throwing twin.** A throwing `evaluate_series` would have to drop the position into `ArithmeticException`, and a spelling that loses the most useful fact is worse than none.

**Ruling: accepted as recommended.**

### S9. Binning: bounded capacity, `BandTable` classes, counts, and a miss is a miss. **SPIKE (vector alternative)**

**Recommendation:**
- The input is `MeasuredObservations<Q, Capacity>`: at most `Capacity` present values, with a runtime count.
- The classes are a `BandTable` (half-open, validated by the shipped `RequireValidBandTable`, `band.hpp:309`), reused and not rebuilt, exactly as phase 11's C4 ruled.
- The output is a series of **counts** in `unit::One`, of length `Classes.size()`, so binning turns a runtime-count input into a static-length output.
- An observation that falls in no class is a **miss**: `DomainError` at that observation's position. It is never dropped.
- Fractions per class are the author's algebra: `binned<…>(o) / sum(binned<…>(o))`.

**Why a bound and not `std::vector`:** the same `noexcept`/`bad_alloc` reason as S1, plus constexpr testability. Filling past capacity at runtime returns `std::unexpected`, never an abort.

There is no default capacity. The author states `Capacity`, the way the author states `N`.

**Spike result:** a transient `std::vector` in a constant expression *does* compile on all five measured. It passed at N = 64 on all five, and at 256 on cl 19.51, clang-cl and clang++ 22.1.3. So the bounded capacity rests on the `noexcept` → `std::terminate` reason alone, not on constexpr support.

**Ruling: accepted as recommended.**

### S10. Snapping: a `BreakpointTable` permitted set, nearest by distance, an explicit tie rule, and a miss outside the set

**Recommendation:** `snapped<KeyUnit, Permitted, SnapTie>(operand)` is a scalar `Node`:
- `Permitted` is a `BreakpointTable` (`lookup.hpp:1360`), validated by the shipped `RequireValidBreakpointTable` (ascending, distinct, well-formed) plus one new refusal: it must not be empty.
- "Nearest" means the smallest absolute difference, in `KeyUnit`.
- The tie rule is a **required** template argument, `SnapTie::TowardLower` or `SnapTie::TowardHigher`, with no default. A value exactly midway between two permitted values is ordinary data, and `RoundingMode` already set this project's precedent of naming the tie rule.
- A value **outside `[first, last]`** is a miss (`DomainError`).

**Why a miss:** this is consistent with the interpolating lookup, where "interpolating outside the table's range is not interpolation". A computed value beyond the standardised set is one the method never defined. Quietly snapping 40 mm to a largest permitted value of 13.7 mm is the confident wrong answer this library exists to refuse.

**Not offered:** geometric ("log") nearest. §20.2 lists log-linear interpolation as suspected and unverified, and nothing in the reading established it for snapping.

**Ruling: accepted as recommended**, including the out-of-range miss.

### S11. Curves and splicing

**Recommendation:**
- A **curve** pairs a domain series with a value series of equal length: `curve(domain, values)`, satisfying `concept CurveExpression`.
- `domain<KeyUnit, Points>()` is a series whose elements come from a `BreakpointTable` in the type. It is how a method declares its screen set once.
- `splice<Monotone::NonDecreasing>(a, b)`:
  - it produces the **sorted union** of the two curves by domain, with static length `Na + Nb`;
  - two points at the same domain value are a miss at the position where they meet;
  - values must be monotone in the direction the author names, a **required** `Monotone` argument with no default, otherwise the result is a `DomainError` at the first element that breaks it;
  - argument order does not matter, and that is tested both ways (defect class 6).
- **No rescaling at the junction.** If one basis must be scaled onto the other, that is the method's algebra, and the author writes it with elementwise arithmetic before splicing, where the trace shows it.

**Ruling: accepted as recommended.**

### S12. Conformity limits are runtime data, closed at both ends, and either side may be explicitly unbounded

**Recommendation:** `conformity<U>(subject, envelope, verdict, citation = {})` is **not a `Node`**, for `Constraint`'s reason: it produces verdicts, not a quantity.
- The envelope is `Envelope<N>`, one `LimitRow { Limit lower; Limit upper; }` per element, runtime state behind an arity-checked constructor. Each `Limit` is either `limit(Rational)` or `unbounded`. There is no way to write "a limit I forgot to fill in".
- The interval is **closed**, `lower ≤ x ≤ upper`. This differs from `Band`'s half-open rule on purpose: a limit states the least and the greatest *permitted* value, where a band partitions a line. The guide says so.
- A row with `lower > upper` makes that element `Invalid(DomainError)`, never `Satisfied` or `Violated`, and the same predicate serves any loader.
- `check_conformity` returns `std::array<ConstraintOutcome, N>` and reuses the four-state `ConstraintOutcome`.

**§16.1 binds here:** the envelope's numbers are the product specification, master data registered per customer. The library supplies the mechanism only. The guide says so, and no test or example carries a limit that resembles a real specification.

**Not in this phase:** a conformity inside a method's `ConstraintSet`, which holds `Constraint`s only (C3 in phase 11).

**Ruling: accepted.** Conformity stays out of `ConstraintSet` this phase. Joining it with method verdicts is recorded as the follow-up **F3: conformity as part of a method's acceptance logic**.

### S13. A method's result stays a scalar

**Recommendation:** a variant must still be a `Node`. A reduction of a series (`sum`, `interpolate_at`, `snapped`) is one, so it can be a variant, overlaid and vocabulary-scoped. A method reporting a whole series is deferred. `evaluate_method` returns `Evaluated<Rep>`, and a method-level series result would need a series rounding rule and a series `VariantSelected` step, which is a phase 11 redesign. Task 2 turns "a series given to `variant<Tag>`" and "a series given to `checked_evaluate`" into this library's own message.

**Ruling: accepted.**

### S14. Rendering: a series variable carries an index marker in the formula itself. **SPIKE decides the spelling**

**Original recommendation (overruled):** no index marker, with seriesness shown only in the symbol table and the trace.

**Ruling: overruled.** A reader of the rendered formula must be able to tell a series from a scalar *in the formula itself*; the symbol table is not enough. **A marker must exist.** Task 1's spike **decides the exact spelling**.
- **Decided by the spike (task 1, `task-1-spike.md`):**
  - LaTeX **`{x_m}_{i}`**: the whole symbol braced, then `_{i}`.
  - Plain **`x_m(i)`**.
  - Markdown **`` `x_m(i)` ``**, with the marker inside the backticks.

  Measured:
  - MathJax 3.2.2 with the site configuration, and with `noundefined` removed, typesets `{x_m}_{i}`, `{R}_{i}`, `{f_{c}}_{i}`, `{x_m}_{i}^{2}` and the marker inside `\frac`, `\sum` and `\operatorname{…}`. The index attaches to the whole symbol.
  - tectonic 0.17.0 with `[OT1]{fontenc}` compiles all of them.
  - Both engines reject `x_m_i` ("Double subscript").
  - python-markdown 3.10.3 keeps `` `x_m(i)` `` literal.
  - `x_{m,i}` also typesets, but it needs the symbol's own subscript rewritten, and the library cannot parse an arbitrary vocabulary string.
  - Known limit: a symbol that already ends in `)` (`w(t)`) reads `w(t)(i)`. Task 3 pins that case, and the guide names it.
- The spike may choose another marker if that one fails. The marker it chooses must typeset correctly under **MathJax 3.2.2** (the site's pinned version) and under **tectonic with `\usepackage[OT1]{fontenc}`**.
- It must also pass the Markdown guard (`render_tests.cpp:1313`): no bare `[`, and no `](`.

**What a marker must not be, and why:**
- `m_r[i]`, because the Markdown guard forbids a bare `[`.
- `x_m_i`, because a symbol that already holds `_` gets a second subscript, which is a TeX error ("Double subscript").

**Where the marker appears:**
- The **series variable** is marked: `m_r(i) / m_t`, `sum(m_r(i))`, `cumulative(m_r(i), from last)`.
- Operations take their meaning from their operands, so an elementwise node adds no second marker.
- A **reduction's** result is a scalar and is unmarked.
- `series_constant`, `domain<…>()` and `binned` output are also series. The spike did not probe these. The recommendation, which task 4 (`series_constant`), task 9 (`domain`) and task 10 (`binned`) each implement and read aloud, is that each prints its row list (`domain(0.7, 1.9, … mm)`), which already reads as many values.

The symbol table keeps `SymbolEntry::shape` and `length` as well. The marker tells the reader *that* it is a series, and the table says *how long*.

The spellings below are the chosen marker, and each task pins them exactly.

### S15. Representation

Elementwise arithmetic, `cumulative` and `sum` work for any `Rep` through `RepTraits`. Everything that *compares* (snap, conformity, splice, `interpolate_at`, binning) is `Rational`-only, refused with this library's message. That is the banded lookup's precedent (`lookup.hpp:864-872`): a comparison a few ULPs off picks the wrong answer, silently.

**Ruling:** no separate ruling was needed; it follows the existing lookup precedent.

### S16. `Elements<N>` for runtime per-element constants

`series_constant<U>(rat(…), …)` stores an `Elements<N>` member, built with `Corrections<N>`'s two-constructor idiom (`lookup.hpp:713`): a short list names both counts, and there is no `{}` default member initialiser (defect class 4). It is a separate type with its own message, because "corrections" is the wrong word for a limit vector. `Corrections` is not modified.

**Ruling:** no separate ruling was needed; it follows the existing `Corrections<N>` precedent.

### S17. Task order: every dependency points backwards

**Ruling:** no step may depend on a node from a later task. Where a step could not move earlier, it moved into the later task, which then carries the join. What moved:

| Step | Was in | Now in | Why |
|---|---|---|---|
| The overlay refusal for a quantity read as a series, and `ConstantRewrite<…, SeriesVarNode>`'s tests | task 3 | **task 5** | needs `sum`, the first series-holding `Node` a method variant can hold |
| The elementwise node in the vocabulary suite's "every node kind" method | task 4 | **task 5** | a method variant must be a `Node` (S13), so it needs `sum` |
| The computed-input snap case, `snapped<…>(interpolate_at(…))` | task 8 | **task 9** | needs `interpolate_at` |

Swapping tasks 4 and 5 was considered and rejected. Task 5's own fixtures (passing % as `100 % − cumulative(…) / m_t`, and `m_r(i) / sum(m_r(i))`) need task 4's elementwise arithmetic, so a swap would only reverse the dependency.

After the move, every dependency points backwards:
- tasks 6, 7 and 9 use task 4's elementwise arithmetic and task 5's `cumulative`;
- task 10 uses task 5's `sum`;
- task 9 carries task 8's snap join.

Task 1's spike uses stand-ins only and depends on nothing.

## Global Constraints

- **C++23**, header-only, no dependency beyond the standard library in shipped headers (§3).
- Must compile on **MSVC cl, clang-cl, clang++ and GCC**. Verify every task on all eight presets: `cl-debug`, `cl-release`, `clangcl-debug`, `clangcl-release`, `clang-debug`, `clang-release`, `gcc-release`, `clang-ubsan`. Iterate on `cl-debug` + `gcc-release`, and hand in after the controller's `verify_all.ps1 -Root <tree>`.
- **Doxygen 1.9.8 (in WSL), zero warnings, and `mkdocs build --strict` (Windows Python) on every task**, not only before the merge.
- **No norm content** (§3): no identifiers, clause numbers, equations, thresholds, limit envelopes or **sieve sizes** from any real standard. Cite invented `Example Standard` references only. Fixture apertures are the deliberately irregular **0.7, 1.9, 3.3, 7.1, 13.7 mm**, chosen *not* to form a geometric progression. Binning classes are **0 to 1, 1 to 2 and 2 to 5 mm**. Do not "tidy" them into round or preferred numbers.
- **No abort, terminate or assert pop-ups.** Refusals are compile-time `static_assert`s in this library's words, or runtime results. Nothing new may `throw` from a `noexcept` path. Examples link `support/fail_without_dialogs.cpp` (already done by `formula_add_example`).
- **Never hardcode `/std:c++23`.** Never redirect a build to `/dev/null`. `FORMULA_WERROR=ON` everywhere.
- Every negative test asserts **both** that the build fails **and** that the output holds this library's own `static_assert` text. Every negative test gets a **deletion check**: delete the guard, confirm the case compiles, restore with a plain write or `touch`.
- **No `{}` default member initialiser on any member that holds an expression or a node** (defect class 4). That covers every series node's operand, a curve's two series, a conformity's subject, an observation node and a snap's operand. `Elements<N>` and `Envelope<N>` also have no `{}`.
- **Names.** Under GCC `-Wshadow`, no parameter or local in namespace `formula` code may be named after a namespace-scope entity this phase adds: `series`, `sum`, `cumulative`, `curve`, `domain`, `splice`, `snapped`, `binned`, `observations`, `conformity`, `envelope`, `unbounded`. Under cl C4459 (afcbf88's finding), follow afcbf88's renaming convention for new locals and parameters, and avoid `result`, `value`, `index`, `text`, `step`, `first`, `mark`, `position`, `numerator`, `denominator`, `lhs` and `rhs`. Check every new `StepKind` enumerator on GCC under `-Wshadow`, as `PiConstant` had to be.
- Every new header goes into the install `FILE_SET` (`hygiene.installed-headers` fails otherwise) and into `formula.hpp`. `trace.hpp` and `document.hpp` stay out of the umbrella.
- **Coherent SI and the method's rounding decide every fixture** (defect class 5). A value is stored in coherent SI (grams become kilograms, percent becomes a fraction), and every assertion names the plausible wrong implementation its value tells apart.
- `unit::Percent` emits a bare `%` in LaTeX. That is a known, tracked follow-up (STATUS.md) and is **not fixed in this phase**. No test may pin a LaTeX string containing it as correct; use `unit::One` fractions in LaTeX assertions.
- A quoted compiler diagnostic in `docs/` must come from a real compile (`hygiene.documented-diagnostics`). Every ```` ```text ```` block in the guide must be whole consecutive lines of the example's real output.

## The shared fixture

Tasks 4–10 use one invented screen analysis, written out once here so that no task re-derives it. `Retained` (`"m_r"`, grams), `TotalMass` (`"m_t"`, grams) and `Passing` (`"p"`, `unit::Percent`) are invented quantities. The five screens, in ascending aperture, are 0.7, 1.9, 3.3, 7.1 and 13.7 mm. The total mass is 1250 g.

**Why 1250 g and not 1000 g** (a correction made during task 5): 1000 g is exactly 1 kg, which is 1 in coherent SI, so "divide by `m_t`" could not be told from "divide by one" -- a defect that skipped the scalar would pass every test that relied on dividing by the total. A mutation in task 4 showed it. 1250 g is 1.25 in SI: not 0, not 1, not a power of ten.

## Corrections made during execution

Found by review while tasks 8–11 ran. The shipped code, tests, example and guide follow these, not the text above where the two differ.

- **Fixture values (defect class 9).** The screens above, 0.7, 1.9, 3.3, 7.1 and 13.7 mm, the fine curve task 9 splices, 0.02, 0.09 and 0.3, and task 10's binning classes, 0 to 1, 1 to 2 and 2 to 5 mm, all have the digits of real test-sieve apertures in some unit. Moving them into metres (task 8's M2) made them implausible but kept the digits. The fixtures now use invented primes, which are not a sieve size in any unit:
  - screens of 11, 29, 41, 59 and 83 m;
  - a fine curve at 1/3, 5/3 and 13/3 m;
  - classes of 0 to under 11, 11 to under 29, and 29 to under 83 m.

  Every expected value was recomputed. With the retained masses above, 47 m reads 4912/75 %, the inverse curve at 50 % reads 1111/35 m (snapped: 29 m), and 6 m across the splice's join reads 19.59 %. The lead's first example set, 11, 23, 37, 53 and 71 m, was not used, because 53 and 71 are test-sieve sizes in micrometres. The table above keeps its millimetre values as the arithmetic record of tasks 4–7.
- **Splice (task 9 review).** Duplicates are judged over the whole union first, and the direction only after that, so a failure's position does not depend on argument order (M1). An operand curve's failure is relayed with no element (M2). A failed curve's trace line names the point and the rule, `[duplicate domain point 7 m]` or `[breaks non-decreasing at 11 m]` (L1, `Step::curveBreak`).
- **Failure positions downstream (task 10).** A binning's failure names an observation, not a count. Every series operation relays an operand's failure through `detail::relayed_failure`, which drops a position that is not one of the operand's elements. After the task 10 review (M4), `SeriesFailure` carries `FailureSite { ResultElement, InputObservation }`: a binning's failure is marked `InputObservation`, the trace reads "at observation k" or "at element k" to match, and `relayed_failure` drops an `InputObservation` position. Task 10 also refuses a binning with no classes (`RequireBinnedClassesNotEmpty`), as `series<Q, 0>` is refused.
- **Binning's rendering (S14).** `binned` renders as `bin(s(i), <class>, ...)`, with the observations marked as a series variable is and each class spelled as a band. It does not print a row list.
